Measure how much effort a coding agent spends to build software.

agent-bench gives a coding agent the same task under different conditions, such as a framework, a skill set or a model, and counts every model call it makes through one metering proxy. Effort is measured the same way whichever agent builds, so builds can be compared across frameworks, builders and models.

How it works

One build = one task, under one arm, by one builder, for one repetition.

1 · Experimentexperiment.toml

Lists the tasks, the arms, the builders and the repetitions, plus the protocol, how many builds run at once (lanes), a token budget, gates such as a disk or credit check, and the proxy's upstreams. The runner expands it into builds and gives each build its own port.

2 · Workspacetask.toml

A fresh git repository per build: a git archive of a fixed ref, with every existing arm stripped except shared files the task keeps. The builder writes only into its slot, the arm's directory. The base is committed, so the build's change is final.patch against it.

3 · Prompttask + arm

The task's spec, then the arm's framework section, then the machine notes with the extras: the slot line, the arm's notes, and the success criterion with a self-check command. Every arm of a task gets the same spec, byte for byte. Skills are installed where each agent looks for them.

4 · Builderadapter

Each adapter runs its agent headless, with its own HOME and config under the build directory so the user's settings never leak in. It handles resuming a session, crashes, retries and rate-limit waits, and keeps the agent's native transcript.

5 · Meteringproxy

The agent's base URL points at the proxy, under a path that names the build and the role (builder or driver). The proxy forwards each call and records the usage the API itself returned, streamed or not. This ledger is the measure.

6 · Acceptanceprotocol

The benchmark's own harness runs the builder's arm and writes a verdict. The protocol decides what happens next: stop (one-shot), send the failure back (accept-loop), or have a Claude Code driver review first (reviewed).

7 · Analysistrace.jsonl

Every transcript is normalized into one trace format, so the same analyzers work for any agent: tool calls by kind, skills opened, reads of the framework's installed source, paths touched outside the workspace, and runs of named commands with their error rate.

The measure

Effort is the tokens the builder's model calls cost, as the API reported them.

tokens.builder.total = uncached input + cache reads + cache writes + output, summed over every model call the builder made.
  • Metered, not self-reported. The proxy reads usage from each API response. The agent's own count is kept beside it as a cross-check, never as the measure: agents differ in what they count (side calls, sub-agents, cache semantics), and some report nothing.
  • One schema for every API. Anthropic's input_tokens excludes the cache; OpenAI's prompt_tokens and Responses' input_tokens include it. Both are normalized into the same four parts. A streamed Chat Completions call that would report no usage gets stream_options.include_usage added, and the call is marked.
  • Cache reads count. Each call re-reads the session's context, so a long session pays twice: more calls, and more context per call. Counting cache reads keeps that visible; the four parts are also stored separately, so a cost-weighted view is one step away.
  • Per role. The proxy path carries the role, so a reviewing driver's tokens are counted apart from the builder's. A budget can cap either or both.
  • Auth is unchanged. The proxy can hold the real API key so the builder only sees a dummy. Without one, the client's own login passes through, so subscription logins (Claude Code, Codex on ChatGPT) are metered too.

Alongside tokens, each build records model calls, wall time, the number of rounds and acceptance runs, lines added and removed in the arm, and the trace analyzers' counts.

Evaluation methodology

What is held fixed, what varies, and what a comparison can and cannot claim.

What varies, and what does not

The arm

The condition under test: a framework's section of the prompt, its skills, its notes, and the patterns that mark a read of its installed source. One arm per framework, or per skill version.

The builder

The coding agent and its model, through an adapter. The same task pack runs under any builder; only the skills directory differs, and the prompt names it through ${skills_dir}.

Fixed per task

The repository ref, the stripped workspace, the spec text, the machine notes, the environment, the acceptance check and its bar. A dry run writes every prompt and workspace without calling a model, so they can be diffed before spending anything.

Keeping a comparison fair

  1. Same text, same check. Every arm of a task gets the same spec and success criterion, and is judged by the same acceptance command. The criterion is told to the builder, with the command it can run to check itself.
  2. Same instructions on when to stop. A pass condition is not a stop instruction: builders keep improving after they have passed unless the prompt says to stop. In one study, a build spent 60% of its tokens after it had already passed. Give every arm the same finishing instruction, or measure tokens up to the first passing self-test.
  3. Isolation. A fresh workspace per build, a private agent config, a port per build, and lanes so builds that share a service run one after another. Any tool call touching a path outside the workspace is recorded as peeking.
  4. Repetitions. Builds are not deterministic. Compare means over repetitions, and read a single build as one sample.
  5. Two models, two roles. The builder model writes the code; the app model is what the built agent calls during self-tests and acceptance. Builder tokens do not depend on the app model, but pass rates do, so report the app model with every pass rate.
  6. A budget, when needed. A token budget per build, the same for every arm, stops a runaway build mid-turn and marks it over-budget.

Limits of the measure

  • Tokens are not dollars: providers price cache reads, writes and output differently. The parts are stored, so cost can be recomputed per price list.
  • A builder that knows a framework from pre-training reads less. Source reads and skill use show how much each builder had to look up.
  • Self-tests and acceptance run a model too. When the app model is noisy, a builder may re-run checks to confirm stability, which shows up as effort.

Protocols

How the builder's turns, a review and the acceptance checks fit together in one build.

one-shot

One builder session, then one acceptance check, pass or fail. No feedback. The cleanest measure of effort.

rounds = 1

accept-loop

Builder, then acceptance. On failure the check's reasons and log go back to the same session, up to max_rounds times. No driver.

rounds = acceptance runs

reviewed

Builder, then a Claude Code driver reviews and answers DONE or CONTINUE with feedback. A DONE goes to acceptance, and a failure goes back to the builder.

rounds = driver verdicts

A build ends as works, done-not-working, incomplete, over-budget or error. The runner resumes an interrupted experiment by skipping builds that already have a summary.

Use it

Requires jac 0.37.25, the version jac.toml pins. The agents themselves are installed separately.

jac install --dev                      # aiohttp, textual, pytest into .jac/venv
export PATH="$PWD/bin:$PATH"           # bin/agent-bench runs the CLI under jac

agent-bench agents                     # which builders are installed
agent-bench run exp.toml --dry-run     # write every workspace and prompt, call no model
agent-bench run exp.toml               # run the experiment
agent-bench monitor                    # live view of everything running
agent-bench report runs/exp --by arm,builder
agent-bench serve                      # API + web UI on 127.0.0.1:8770
agent-bench tui                        # the terminal UI

A minimal experiment

run_id   = "wordfreq-skills"
tasks    = ["tasks/wordfreq"]
arms     = ["arms/stdlib.toml", "arms/stdlib-skill.toml"]
protocol = "one-shot"
reps     = 3
lanes    = 6

[proxy]
port = 8780
[proxy.upstreams.anthropic]
url = "https://api.anthropic.com"
api = "anthropic"

[[builders]]
name     = "cc-sonnet"
agent    = "claude-code"
model    = "claude-sonnet-5-5"
endpoint = "anthropic"
